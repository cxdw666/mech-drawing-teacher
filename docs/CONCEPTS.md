# 概念对照：我们做的每件事，在 agent 里叫什么

> 这份文档解决一个问题：你知道"要跑 node tools/eval.mjs"，但不知道**这在 agent 工程里是什么环节、为什么必须做**。
> 左边是我们仓库里真实存在的东西，中间是通用术语（面试、看论文、读别人项目都用这套词），右边是"不做会怎样"。

## 一、先给你一张地图：一个 agent 由什么组成

```
        ┌─────────────────────────────────────────┐
        │  1. 角色与目标（system prompt / policy）   │  ← 我们：prompts/core-*.md
        ├─────────────────────────────────────────┤
        │  2. 行为约束（guardrails）                │  ← 我们：8~9 条铁律
        ├─────────────────────────────────────────┤
        │  3. 知识与工具（RAG / tools）             │  ← 我们：references/standards-index.md
        ├─────────────────────────────────────────┤
        │  4. 输出契约（structured output / schema） │  ← 我们：六步契约 + 六件套版式
        ├─────────────────────────────────────────┤
        │  5. 评测与迭代（evals / ablation）         │  ← 我们：evals/ + tools/eval.mjs
        └─────────────────────────────────────────┘
```

大部分教程只讲第 1 层（"写个好 prompt"），因为那一层最容易出效果。**真正决定它三个月后还能不能用的是第 5 层**，而第 5 层最难，因为它要求你先承认"我不知道它到底行不行"。

## 二、逐项对照

| 我们做的事 | 通用术语 | 这是什么 | 为什么这么做 |
|---|---|---|---|
| `prompts/core-vX.md` 单独成文件 | **system prompt / policy** | 给模型的常驻设定，决定它的身份、边界、优先级 | 单独成文件才能版本化、diff、回滚。写在一个网页对话框里，你改到第五版就分不清哪版是你满意的 |
| 8~9 条「铁律」 | **guardrails / constraints** | 硬性行为约束，优先级高于普通指令 | 模型会为了"帮忙"而越界。约束必须显式、可判、放最前面 |
| 铁律写成「必须带 XX 标记」而不是「不许假装」 | **可验证约束（verifiable constraint）** | 把"态度"翻译成"输出里必须出现的东西" | "不许假装画对"无法判定；"示意图首行必须写不按比例"一眼能查。**凡是约束，都要能被检查** |
| 六步契约、六件套版式 | **structured output / output contract** | 规定回答的结构，而不只是内容 | 结构可判定、可对比、可自动校验；自由散文无法比较两版谁更好 |
| 「先判后画」「六步不可跳步」 | **process constraint / chain-of-steps** | 约束推理顺序 | 让模型先分解再作图，等价于 hand-written chain-of-thought，比"请仔细思考"有效得多 |
| 铁律 7「必须至少追问 1 个」 | **clarification policy** | 信息不足时的行为规范 | 不给模型"问"的义务，它就会用假设把空白填满并当成事实输出——这是幻觉的主要来源之一 |
| 降级表（要 DWG → 给参数化草图） | **graceful degradation / fallback** | 超范围请求的处理路径 | 没有降级路径的 agent，只有两种表现：硬答或拒答，都伤用户 |
| `references/standards-index.md` | **知识检索层（RAG 的前身）** | 告诉模型"去哪查"，而不是塞给它全部知识 | 塞 500 页标准它只会记住开头三页；索引 + 按需检索，命中率更高、可维护 |
| 「不在索引里的标准号只能说没有」 | **grounding / 抗幻觉约束** | 把回答锚定在给定材料上 | 模型不知道"自己不知道"，必须由外部清单给它划边界 |
| `evals/cases.json` | **测试集 / golden set** | 固定输入 + 固定判据 | **没有测试集就没有"更好"的定义**。你改一句提示词，凭什么说它变好了？ |
| `evals/round-N.md` 的判据是好/不过 | **二值判据（binary rubric）** | 可判定标准，而非主观评分 | "答得不错"无法复现；"有没有出现『严禁画粗实线』"可以 |
| `--runs 3` | **稳定性评估（非确定性测试）** | 同一输入多次运行 | 模型按温度采样，同输入不同输出。否定约束的失效是**概率性**的，1 次过是运气，3 次过才算约束成立 |
| 只改一句，再跑同一条用例 | **消融实验（ablation）/ 单变量对照** | 控制变量，验证某句话是否承重 | 一次改两句，你永远不知道是哪句起的作用。这是提示词工程里唯一能证明"这句话有用"的方法 |
| `prompts/exp/*-test.md` | **实验分支 / 灰度** | 未验证的改动放旁支 | 主干永远可发布；实验失败直接删，不污染版本历史 |
| `evals/results.md` | **评测报告（eval report）** | 结果与证据留档 | 发布时它就是可信度。别人信的不是你的形容词，是"它在这些用例上是这样" |
| 3-2「歧义输入」用例 | **回归测试（regression test）** | 防止修好一个、弄坏另一个 | 加了版式后，模型可能为了凑格式而跳过追问——这条用例就是拦它的 |
| 版本锚 + CHANGELOG | **语义化版本 + 变更记录** | 模块增删记 minor，措辞修正记 patch | 提示词是代码，就该有版本；否则"上周还挺好的"永远查不到原因 |
| `tools/eval.mjs` | **评测执行器（harness）** | 批量跑用例、落盘原始输出 | 人眼判 3 条还行，判 30 条就不现实；规模一上来，工具是必需品 |
| 空输出/截断判失败 | **失败要显式** | 不把"没拿到结果"当成"通过" | 静默失败比报错危险：你会以为它过了。我们真踩过这个坑（4000 tokens 被思考过程吃光，正文为空却记了"过"） |

## 三、你现在缺的三块知识（按对本项目的影响排序）

1. **评测思维（eval thinking）**
   核心问题不是"怎么让它更好"，而是"**怎么知道它变好了**"。没有测试集和判据，所有提示词改动都是玄学。
   → 本项目对应：`evals/`、`tools/eval.mjs`、`results.md`

2. **约束的可验证性（verifiability）**
   凡是写成"不许/要仔细/尽量"的约束，等于没写。约束必须落成输出里能看见的东西。
   → 本项目对应：铁律 3 的标记、铁律 7 的追问数、铁律 2 的索引核对

3. **上下文工程（context engineering）**
   提示词不是越长越好。每加一句都要问：它承重吗？删掉会怎样？
   → 本项目对应：`prompts/exp/` 消融实验、`max_tokens` 与输出长度、为什么把标准表放外部而不是塞进提示词

## 四、这些概念怎么迁移

同一条流水线换到别的 agent 上完全一样：

```
写角色 → 写约束（每条配可观察动作）→ 定输出结构 → 建 5~10 条用例 → 三跑记录
   ↑                                                              ↓
   └──────── 只改一句 ← 判据不过 ← 找出失效形态 ←──────────────┘
```

差别只在"约束写什么"。客服 agent 是"不许承诺赔付金额"，代码 agent 是"改完必须跑测试"，机械制图 agent 是"示意图必须标不按比例"——**方法论是同一套**。
